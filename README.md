# Чек на удачу

Веб-приложение промо-акции на Python 3.14, Django 6.0, PostgreSQL 17 и Docker Compose.
Пользователь регистрирует чек, модератор проверяет его в Django Admin.

## Запуск

```sh
cp .env.example .env
# Заполнить секреты, пароли и даты акции в .env.
docker compose up --build -d
```

Миграции, зависимости и collectstatic выполняются исходным entrypoint автоматически.
Адрес: http://testtask002.localhost/ (домен *.localhost указывает на loopback).
Если браузер не разрешает домен, добавьте 127.0.0.1 testtask002.localhost в hosts.
Порт 80 должен быть свободен; альтернативный порт можно задать через APP_PORT.
Главная страница требует входа и перенаправляет на /accounts/login/.

Использован исходный local-деплой: Traefik → Caddy → Django под Supervisor,
PostgreSQL, pgAdmin, Mailpit, cron и logrotate. Файл docker-compose.local.yml
подключается из compose.yaml. Все сервисы, сеть и volumes используют testtask002.
Код монтируется из application/. Media хранится в application/media.
Локальные настройки находятся в deploy/application/local/.

```sh
docker compose logs -f testtask002_application
docker compose down
```

Остановка сохраняет данные. docker compose down -v удаляет данные проекта.
Это local-окружение; публичный production-деплой требует HTTPS и отключения DEBUG.
Изменение POSTGRES_PASSWORD после первого запуска требует изменения пароля роли в самой БД;
переменная окружения автоматически не меняет существующую роль. Аналогично для pgAdmin.

## Аккаунты и модерация

Регистрация: /accounts/register/. Вход: /accounts/login/. Выход — POST с CSRF.
Модератору нужны is_staff и права view_receipt/change_receipt:

```sh
docker compose exec testtask002_application /opt/venv/bin/python manage.py create_moderator moderator
# Команда интерактивно запросит пароль.
```

При необходимости полный администратор:

```sh
docker compose exec testtask002_application /opt/venv/bin/python manage.py createsuperuser
```

Админка: /admin/. Модератор видит все чеки, ищет по реквизитам/логину,
фильтрует по статусу и датам, меняет статус и причину отказа.
Реквизиты и владелец в интерфейсе модерации доступны только для чтения.
При отклонении обязательна непустая причина; при смене статуса причина очищается.

## Реализовано

- Стандартная Django-авторизация, регистрация, вход и выход.
- HTML/Django-шаблоны: кабинет, форма регистрации чека, пустое состояние, успех.
- Адаптация для 375 px без горизонтального скролла.
- Форма с JS-проверкой обязательных полей и форматов, отправка через fetch с CSRF.
- Серверная проверка реквизитов, даты, суммы от 1 000 ₽ и повторной регистрации.
- Decimal для денег; уникальность ФН + ФД + ФП на уровне PostgreSQL.
- Конкурирующий дубль возвращает понятную ошибку вместо 500.
- Новый чек получает текущего владельца и статус «На проверке» независимо от входных параметров.
- Кабинет содержит только свои чеки, новые регистрации первыми, пагинация по 10.
- GET /api/receipts/ — JSON с чеками владельца и пагинацией; без входа 401.
- Чужие user/user_id/demo-параметры не меняют владельца выборки.
- Период акции из .env выводится в интерфейсе.

## Настройки и спорные решения

PROMO_START и PROMO_END задаются в формате YYYY-MM-DD. Обе границы включены полностью.
TIME_ZONE задаёт часовой пояс акции. Время из datetime-local интерпретируется именно
в этом часовом поясе, который указан под формой; время клиента не меняет смысл покупки.
В PostgreSQL даты хранятся как timestamptz, в кабинете отображаются в часовом поясе акции.
Отклонённый чек повторно отправить нельзя: уникальность реквизитов действует для всех статусов.
При изменении результата модератор редактирует существующий чек.
ФН — ровно 16 цифр; ФД и ФП — от 1 до 10 цифр. Ведущие нули сохраняются.
Дробная часть суммы — максимум два знака; запятая принимается и нормализуется в точку.
Статус «Вы выиграли» из макета не используется: в задании нет механики розыгрыша.
Государственная проверка достоверности чека/ФНС в задании не требуется и не выполняется.

Секреты хранятся в .env, который исключён из Git. .env.example содержит только примеры.
Настройки БД и pgAdmin читают пароли из окружения.

## API

```text
GET /api/receipts/?page=2
Cookie: sessionid=...
```

Ответ: count, page, pages, results. Каждый чек содержит id, fn, fd, fp,
purchased_at, amount (строка Decimal), status, status_label, rejection_reason и created_at.
Параметр page нормализуется Django Paginator; некорректная страница не вызывает 500.

## Тестовые данные

0001_initial создаёт модель и ограничения. 0002_demo_receipts создаёт 24 чека
для demo_elena и 6 для demo_alexey с разными суммами и всеми тремя статусами.
Даты находятся в периоде акции на момент первого применения миграции.
0003_demo_chronology помещает демонстрационные регистрации в прошлое,
чтобы вновь добавленный чек появлялся первым.
Все тестовые чеки отмечены is_demo=True. Пароли в миграции отключены.
После изменения периода акции ранее созданные даты автоматически не меняются.

Чтобы включить тестовые аккаунты, задайте DEMO_PASSWORD и DEMO_MODERATOR_PASSWORD в .env:

```sh
docker compose up -d testtask002_application
docker compose exec testtask002_application /opt/venv/bin/python manage.py prepare_demo
```

prepare_demo устанавливает пароли demo_elena/demo_alexey и создаёт staff demo_moderator
с правами просмотра и изменения чеков. Пароли не выводятся в логи.
Тестовые данные удаляются обратной миграцией: migrate receipts 0001.
Тестовый модератор создаётся отдельной командой и при откате seed-миграции не удаляется.

## Проверки

```sh
docker compose exec testtask002_application /opt/venv/bin/python manage.py test receipts --noinput
docker compose exec testtask002_application /opt/venv/bin/python manage.py check
docker compose exec testtask002_application /opt/venv/bin/python manage.py makemigrations --check --dry-run
```

17 тестов проверяют границы периода, часовой пояс, реквизиты, деньги, дубли,
ошибку дубля на уровне БД, ограничения PostgreSQL, владельца, пагинацию,
авторизацию, CSRF, регистрацию/вход/выход и модерацию через admin.
Для временной тестовой БД локальной роли предоставлено CREATEDB через init.sql.

## Сверх задания

- CSV-выгрузка выбранных принятых чеков из админки (UTF-8 с BOM).
- Сортировка кабинета по дате покупки, сумме, статусу или дате регистрации.
- Обратимая миграция тестовых данных и команда создания модератора.
- Тесты валидации, ограничений БД, изоляции пользователей и модерации.

QR-разбор, фотографии и автоматическое обновление статуса не реализованы:
это необязательные пункты PDF. Обязательная часть реализована.
Историю коммитов и публикацию репозитория выполняет владелец проекта.

## Работа с ИИ

ИИ помог с Django-каркасом, HTML-шаблонами, формами, API и автоматическими проверками.
Первоначально ИИ ошибочно заменил готовый local-деплой и генерировал таблицу в JS:
это обнаружилось при просмотре проекта; исходная инфраструктура восстановлена,
а интерфейс разделён на обычные Django-шаблоны. Первый тест регистрации использовал
пароль, похожий на логин; стандартный валидатор отклонил его, тест исправлен.
При наличии большего времени стоит вынести дату/правила акции в отдельный слой,
добавить обработку реальных QR-кодов и углубить тесты конкурентных запросов.
